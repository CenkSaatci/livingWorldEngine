# Audit 2026-09-23 — POI-Aktionen, Währung, Händler (ADR-015)

- **Scope:** Feature-Diff `db2040b..HEAD` (3 Commits: Backend/Schema, Frontend, Doku) + UI/UX-Sicht via Playwright gegen die QA-Welt.
- **Methode:** `find-bugs`-Checkliste (Injection/XSS/Auth/IDOR/Race/DoS/Business-Logik) + Playwright-E2E (`frontend/e2e/poi-audit.spec.ts`, 7 Tests grün) inkl. A11y-Heuristiken (Buttons/Inputs ohne Namen, Overflow, `undefined`/UUID-Leaks).
- **Stand:** Backend-Suite grün (inkl. 4 neuer Testklassen für ADR-015), Frontend 219 Tests, `tsc` clean. Die Befunde sind nicht durch Tests abgedeckt (siehe Test-Lücken).
- **Hinweis:** Für die UI-Prüfung wurde eine **isolierte Demo-Welt** per API vorbereitet; sie scheiterte am Welt-Limit. Stattdessen wurde die QA-Welt **nur lesend** genutzt; ein temporärer Audit-Händler wurde nach dem Nachweis wieder gelöscht. Es wurden keine Produktdaten verändert.

## Kritisch / Hoch

### H-1 — Item-Auflösung bricht bei gepinnter Kampagne (Feature unbenutzbar)
- **Datei:** `backend/src/main/java/com/lwe/core/service/RulesLoader.java:53-58` (View), betroffen `PoiActionService.java:426`, `MerchantService.java:80,176,191`
- **Severity:** High
- **Problem:** `loadSystemByCampaign` baut bei vorhandenem `rulesJsonSnapshot` eine `GameSystem`-Sicht über den Konstruktor `(name, version, rulesJson, schemaJson)` — die **ID wird nie gesetzt**. `resolveSystem(...).getId()` ist damit `null`; `itemRepo.findByGameSystemId(null)` findet nichts. Item-Effekte werfen `POI_ITEM_UNKNOWN`, das gesamte Händler-Sortiment wird `resolved=false`/`price=0` und ist nicht kaufbar.
- **Evidence (empirisch):** QA-Kampagne `42ff88d5…` pinnt System `7fd06281…` (Version 4). Item `QA-Schwert` existiert (Wert 50). Ein temporärer Händler am QA-Dorf lieferte:
  `{"item":"QA-Schwert","itemId":null,"price":0,"sellPrice":0,"resolved":false}`.
  Der Fall ist der **Normalfall** — `CampaignService.create` setzt den Snapshot immer.
- **Fix:** In `RulesLoader` die ID mitkopieren, z. B. `view.setId(system.getId())` (Setter ergänzen) oder einen Kopier-Konstruktor mit ID. Root-Cause-Fix an einer Stelle, wirkt für alle Aufrufer. Zusätzlich einen Test ergänzen, der `resolveSystem` mit Snapshot gegen `getId()`/Item-Lookup prüft (siehe T-1).

### H-2 — Unbegrenzte Menge + Integer-Overflow beim Kauf/Verkauf
- **Datei:** `backend/src/main/java/com/lwe/core/service/MerchantService.java:121,147`; Eingabe `MerchantController.TradeRequest.qty` (kein `@Max`)
- **Severity:** High (Wirtschafts-Integrität), mittel (DoS)
- **Problem:** `int total = offer.price() * qty;` — `qty` ist unbegrenzt und `int*int` läuft still über. Beispiel: Preis 50, `qty=50_000_000` → `total` negativ → `currencyService.requirePayable(negativ)` steigt sofort aus (`amount <= 0`) → `pay(negativ)` ist ein No-op → `addItemInternal(actor, itemId, 50_000_000)` schenkt 50 Mio. Items. Verkauf analog.
- **Evidence:** Kein `@Max`/Clamp im Controller, keine Obergrenze im Service; `Math.multiplyExact` wird nicht genutzt.
- **Fix:** `qty` hart begrenzen (z. B. `1..10_000` → `TRADE_INVALID_QUANTITY`) und `long`/`Math.multiplyExact` rechnen; bei Überlauf `TRADE_INVALID_QUANTITY`.

### H-3 — `trade.buy`/`trade.sell` und Aktionsbindung werden nicht durchgesetzt
- **Datei:** `MerchantService.buy/sell` (Endpunkte `MerchantController`)
- **Severity:** High (Vertragsbruch)
- **Problem:** Der Katalog erlaubt `trade: {buy:false}`/`{sell:false}` und bindet „Handeln" an einen Ort. Die Kauf-/Verkauf-Endpunkte prüfen weder die Flags noch die Aktionsbindung. Ein System, das Verkauf abschaltet, bleibt per API verkaufbar; gehandelt werden kann mit jedem `is_merchant`-NPC, auch ohne gebundene Aktion.
- **Evidence:** `buy`/`sell` lesen nur `shop_inventory`, `price_modifier`, `sell_rate`; `poi_actions[].trade` wird nur in `defaultSellRate` gelesen.
- **Fix:** Beim Kauf/Verkauf die gebundene „Handeln"-Aktion suchen (Ort/NPC) und `trade.buy`/`trade.sell` prüfen → sonst `POI_ACTION_NOT_AVAILABLE`/`TRADE_DISABLED`.

## Mittel

### M-1 — `dmOnly`-Aktionen samt Beschreibung an Spieler geleakt
- **Datei:** `backend/src/main/java/com/lwe/core/service/PoiActionService.java:108-117`
- **Severity:** Medium (Informationsleck)
- **Problem:** `list` liefert den **kompletten** Katalog inkl. `dmOnly`-Name + `description` an jeden Welt-Leser; die UI graut sie nur aus. Beabsichtigte Leiter-Inhalte werden so verraten.
- **Fix:** `dmOnly`-Aktionen für Nicht-Leiter aus `list` filtern (nicht nur `available=false`).

### M-2 — Basis-Schwierigkeit für `d20_target` ist hart 10
- **Datei:** `backend/src/main/java/com/lwe/core/service/PoiActionService.java:167`
- **Severity:** Medium
- **Problem:** `executeProbe(..., target=10, ...)` — für `d20_target` gilt `success = total >= 10 + difficulty`. Die 10 ist eine Engine-Konstante; Systeme mit anderer Basis-DC können sie nur über `difficulty` ausgleichen. Das ist nirgends dokumentiert und schwächt das Systemagnostik-Versprechen.
- **Fix:** Basis-DC konfigurierbar machen (z. B. `poi_actions[].probe.target` optional) oder in `RULES-SCHEMA.md` als Konvention dokumentieren.

### M-3 — Unbekannter `probe.skill` schlägt nur bei 3W20 fehl
- **Datei:** `PoiActionService.java:163-171`; Validator `RuleSchemaValidator.checkPoiActions`
- **Severity:** Medium (fail-open)
- **Problem:** Für `d20_target`/`d100_threshold` würfelt ein unbekannter Skill mit Modifikator 0 weiter (kein Fehler); nur `d20_3attr` wirft `ROLL_SKILL_NOT_FOUND`. Ein Tippfehler im Katalog bleibt still. Der Validator prüft `probe.skill`/`effects[].condition` nicht gegen `skills[]`/`conditions[]`.
- **Fix:** `probe.skill` vor der Probe gegen `rules.skills[]` prüfen (case-insensitiv) → `POI_ACTION_INVALID`; im Validator unbekannte Skill-/Condition-Referenzen als Fehler (oder mindestens Warnung) melden.

### M-4 — Fehlender i18n-Key: Karten-POI-Button zeigt „editor.actions"
- **Datei:** `frontend/src/pages/MapEditorPage.tsx` (nutzt Namespace `map`), Key fehlt in `frontend/src/i18n/locales/*/map.json`
- **Severity:** Medium (sichtbarer Platzhalter)
- **Problem:** Der Key wurde in `common.json` ergänzt, `MapEditorPage` übersetzt aber mit `useTranslation('map')`. Der neue Button zeigt „editor.actions".
- **Fix:** `editor.actions` in `map.json` (de/en, übrige Sprachen fallen auf en zurück) ergänzen.

### M-5 — Voller Aktionskatalog wird an jedem Ort ausgeliefert
- **Datei:** `PoiActionService.list` (alle Katalog-Einträge, `available=false`)
- **Severity:** Medium (UX + Informationsleck)
- **Problem:** An jedem Ort erscheinen alle Aktionen ausgegraut („Hier nicht verfügbar"). Das ist Rauschen und offenbart das komplette Aktions-Repertoire des Systems an jedem POI.
- **Fix:** Standardmäßig nur gebundene Aktionen liefern; den Rest optional über `?all=true` (für Autoren/Leiter).

### I-1 — `POST /campaigns` → 500, wenn die Welt bereits Beziehungen hat
- **Datei:** `CampaignService.create` → `worldService.cloneForCampaign`
- **Severity:** High (blockiert Mehrfach-Kampagnen)
- **Evidence:** `POST /campaigns` auf die QA-Welt: `500 SYSTEM_INTERNAL_ERROR`, Log:
  `duplicate key value violates unique constraint "entity_relationships_entity_a_id_entity_b_id_key"`.
  Das verhinderte auch den Aufbau einer isolierten Demo-Welt für diesen Audit.
- **Fix:** Beim Klonen Beziehungen deduplizieren (`ON CONFLICT DO NOTHING`) bzw. vorhandene Paare überspringen; Regressionstest „zweite Kampagne in einer Welt mit Beziehungen".
